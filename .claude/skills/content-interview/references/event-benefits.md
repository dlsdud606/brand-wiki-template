# 조회수 기반 이벤트·혜택 기획

이벤트·기획전·쿠폰·증정·체험·댓글/리뷰 행사 요청에 사용한다. 사용자 지정 상품·목적·혜택을 우선하며 순위 때문에 다른 상품으로 바꾸지 않는다. 단순 행사 날짜/문구 수정에는 새 기획 인터뷰를 열지 않는다.

## 인터뷰와 추천 위임

이미 정한 답을 재사용하고, 미정 항목을 묶어 1~3문항으로 묻는다.

- 목표: 관심/조회, 첫 구매, 재구매, 참여, 고객 이해 중 무엇인가? 상품·고객은 지정됐는가, 추천을 맡겼는가?
- 혜택: 가격 할인/쿠폰/묶음/증정/추첨/체험 중 확정 조건·선호·제외 조건은? 추천을 맡겼다면 후보를 비교해 제안한다.
- 운영: 총예산·판매가격·원가/마진·재고·배송 부담·쿠폰 시스템·기간·채널/노출 계획은? 미정이면 필요한 값과 제안 범위를 구분한다.

예산/가격을 몰라도 기획·조건에 의존하지 않는 로컬 시안은 진행한다. 미확정 수치는 `제안`으로 표시하고 확정 혜택 광고/쿠폰 발급/실제 개최로 취급하지 않는다. 전체 인터뷰를 반복하거나 추가 승인을 임의로 만들지 않는다. 기존 제작·유료 생성·발행 권한은 그대로 적용한다.

## 원본 조회수를 근거로 쓰는 절차

1. `raw/reports/이벤트_조회수.xlsx`를 읽는다. `01_knowledge/benchmarks/event-performance.md`는 비교 안내이며 원본과 어긋나면 원본 셀·차이를 보고한다. `proven-content.md`, 해당 `asset-transcripts/`, 원본 이벤트 이미지와 관련 채널 문서를 연결한다. 기존 원본/지식은 수정하지 않는다.
2. 원본 파일·시트·행, 이벤트명·카테고리·시작/종료일·게시기간·총조회수·일평균·링크를 기록한다. URL의 uid는 원본 자산/판독 문서와 연결하는 단서이지 현재 운영 조건의 근거가 아니다. 제목만 보고 할인율/경품/상품 구성을 추정하지 않는다. 이미지가 없으면 구조·혜택을 `자료 없음`으로 남긴다.
3. 총조회수와 일평균을 함께 비교한다. 원본의 `게시기간`은 현재 파일에서 종료일−시작일을 사용한다(달력으로 14일인 행사도 원본 분모는 13일일 수 있다). **원본 분모의 일평균**과 **양 끝 날짜를 포함한 달력일수의 일평균**을 구분해 표기한다. 일수/캐시/날짜 오류는 경고로 남기고 서로 다른 분모를 같은 순위로 섞지 않는다.
4. 같은 상품의 다른 행사 → 유사 카테고리 → 전체 자료 순서로 비교군을 찾는다. 행사 유형·기간·연도/시즌·혜택·구매/참여 조건·노출 경로 차이를 함께 적는다. 유형 분류는 제목 힌트와 원본 이미지 확인을 구분한다. 노출/유입 자료는 없으면 `자료 없음`이다. 비교 가능한 행이 없으면 전체 자료는 참고 사례로만 쓰고 확신을 높이지 않는다.
5. 조회수는 페이지 관심의 관찰값이며 순방문자·참여자·구매·매출·효율과 다르다. 12건처럼 표본이 적고 노출·시즌·상품·기간이 섞인 자료에서 혜택의 인과 효과, 최적 할인율, 예상 전환율/매출을 추정하지 않는다. 단순 종합 점수나 조회수1위 상품을 자동 정답으로 만들지 않는다. 짧은 사전예약의 높은 일평균을 장기 기획전 예상 조회로 그대로 곱하지 않는다.
6. 비교가 실제 추천을 어떻게 바꿨는지 한 줄로 연결한다. 예: 같은 상품의 사전예약에 관심이 몰린 기록은 짧은 집중 소개의 시험 근거가 되지만 재출시 사실이 없는 상품에 사전예약을 적용하거나 할인율을 복사할 근거는 아니다.

### 재사용 추출 도구

실행 도구가 있으면 위키 루트에서 아래 도구를 사용한다. 표준 입력 추출은 읽기 전용이며 JSON만 `deliverables/`에 쓴다. Python `openpyxl`이 없으면 추출기가 Python 표준 라이브러리로 XLSX의 저장된 셀 값을 읽는다. 수식을 다시 계산하지 않으므로 원본 캐시 오류는 경고로 남긴다. 자동 설치나 원본 편집은 필요하지 않다.

```bash
python3 .claude/skills/content-interview/scripts/event_metrics.py --out deliverables/content/<건명>/이벤트조회수_근거.json
```

기본 원본 경로는 스크립트 위치로 찾으므로 프로젝트 루트에서도 실행할 수 있다. `source_*`는 원본 값, `daily_*`는 계산값이다. 날짜 포함 기준의 재계산은 지식 승격이 아니다. 실행 도구가 없는 역할은 주 대화 또는 researcher에게 이 추출 작업만 요청하고 분석 근거를 받는다.

## 후보와 혜택 설계

사용자가 선택했으면 그 안을 발전시키고, 추천을 위임했으면 목적에 맞는 2~3개 후보를 비교한다. 숫자가 없는 중립 후보/혜택 없는 참여안도 가능하다. 할인·증정·추첨·체험을 무조건 모두 묶지 않는다.

| 후보 | 고객이 참여/구매할 이유 | 조회수·원본 사례와 비교 조건 | 혜택/조건 | 비용/운영 부담 | 불확실성 | 선택 이유 |
|---|---|---|---|---|---|---|

혜택 조건에는 적용 상품/구성, 가격 기준, 최소 구매, 할인 상한, 대상/중복/ID 제한, 쿠폰 유효기간, 사은품 수량/재고, 추첨 인원·구매 조건, 경품·발표/배송을 필요한 만큼 넣는다. 실제 가격·조건은 확정값과 제안을 나눈다. 과거 행사 혜택은 비교용이며 현재 사용 가능한 혜택이 아니다.

비용은 알려진 입력으로만 계산한다. 없으면 식과 필요한 값을 남긴다.

- 쿠폰: `대상 주문별 min(쿠폰 적용 금액×할인율, 상한)의 합`. 규모 미정이면 `사용 주문 수×상한`은 최대 할인 부담의 가정 상한이며 실제 비용 예측이 아니다.
- 증정/경품: `지급 수량×(제품 원가+추가 포장·배송비)`.
- 전체: 쿠폰+증정/경품+확정 제작·매체비. 같은 주문의 할인과 쿠폰을 중복 계산하지 않는다.
- 할인 후 공헌이익 검토에는 실제 결제액·상품원가·변동물류/결제비·사은품 부담을 사용한다. 원가가 없으면 이익/ROI를 단정하지 않는다.

## 추천안에서 제작까지

`01_이벤트혜택기획.md`에 비교군 표, 후보 비교, 추천안·다른 안을 택하지 않은 이유, 혜택 조건·예산 식, 기간/발표, 미정 값, 운영 일정, 페이지/팝업 카피 슬롯과 CTA 연결을 작성한다. 브리프·반영표에도 연결한다. 사용자가 추천을 위임하고 제작을 요청했으면 미정 운영값을 확정하지 않고 제안 시안까지 이어간다.

측정 계획은 목표에 맞춰 정한다. 관심: 페이지 조회/노출 자료 확보 후 클릭률. 참여: 유효 참여자와 실제 순방문자 확보 후 참여율. 구매: 실제 순방문자/주문/쿠폰 사용을 확보 후 전환·비용 지표. 원본 조회를 분모로 순방문자 전환율을 만들지 않는다. 혜택 검증 시 같은 상품·기간·유입을 맞추고 한 요소를 바꾸는 비교안을 제안하되 실험 실행은 별도 요청 범위다.

앞선 예시의 10%·5명·14일은 한 번의 제안이다. 다른 이벤트에 고정 기본값으로 복사하지 않는다. 새 요청마다 사용자 조건과 비교 근거로 다시 설계한다.
